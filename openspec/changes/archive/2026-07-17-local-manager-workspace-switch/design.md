## Контекст

У комнаты есть один серверно-авторитетный опубликованный шаг `currentStep`. Его код, язык, брифинг, Yjs-документ, awareness и `syncKey` общие для всех участников. Уже существующий `localStepIntent` хранит личный выбор менеджера, но не изменяет центральную рабочую область.

## Решения

### 1. Два разных контекста, а не два режима общего редактора

`publishedStep` остаётся равным `Room.currentStep` и управляет совместной редактируемой областью. `managerSelectedStep` берётся из локального выбора конкретного владельца или интервьюера. Если они различаются, интерфейс менеджера показывает отдельный статический preview выбранного шага.

Preview не монтирует `RoomCodeEditor`, `BriefingBoard` в режиме записи, Yjs-провайдер, awareness или обработчики изменения языка/брифинга/кода. Это принципиально: даже read-only конфигурация текущего редактора создаёт Yjs-документ и отправляет начальные и периодические снимки, а сервер принимает их только для глобального `syncKey`.

### 2. Отдельный защищённый снимок неактивной задачи

Новый endpoint `GET /api/rooms/{inviteCode}/tasks/{stepIndex}/workspace` возвращает только владельцу или интервьюеру сохранённые данные конкретной задачи: индекс, заголовок, эффективный язык, код и markdown-брифинг. Код и брифинг берутся из сохранённых значений задачи с fallback на стартовый код и описание шаблона.

Кандидат получает `403`. Ответ не добавляется в SSE-объект комнаты: это не раскрывает решения остальных задач каждому подключённому участнику и не раздувает горячий realtime-поток.

### 3. Публикация остаётся единственной общей операцией

Клик по строке задачи сохраняет только `managerSelectedStep` в сессии браузера и меняет локальный preview. Только `Переключить` вызывает уже авторизованную операцию `set_step`.

После публикации кандидат и менеджеры без другого локального выбора показывают новый общий шаг. Менеджер, который уже просматривает другую задачу, сохраняет этот независимый preview; глобальный маркер всё равно перемещается. Когда его локальный выбор совпадает с опубликованным шагом, он возвращается к текущей совместной редактируемой области.

### 4. Рейтинг и глобальные управляющие действия

Во время preview не показываются элементы, которые записывают данные опубликованного шага: синхронное редактирование, изменение языка, общий брифинг, режим фокуса и рейтинг. Личные заметки продолжают быть привязаны к локальному выбору, как и до изменения.

### 5. Контракт управления шагом

Текст доступного только менеджеру действия публикации — `Переключить`. Оно выглядит как компактный pill-тег: полупрозрачный синий фон, синий текст, скругление 999px и без непрозрачной основной кнопки. Маркер опубликованного шага остаётся `Активен`. В aria-label обоих элементов остаётся явный смысл и название задачи.

## Риски и защита

- **Случайная отправка preview в Yjs**: preview строится из статических данных и вообще не использует коллаборативные компоненты.
- **Утечка решения кандидату**: endpoint защищён проверкой `canManageRoom` на сервере; frontend-скрытие не считается защитой.
- **Несвежий сохранённый снимок**: preview документирован как сохранённое состояние неактивного шага. Опубликованный шаг продолжает получать актуальные данные через существующий SSE/Yjs-путь.
- **Конфликт локального выбора и публикации коллеги**: локальный выбор намеренно имеет приоритет для конкретного менеджера; единственный глобальный маркер всегда отражает серверное состояние.

## План проверки

До production-кода расширяется трёхучастниковый E2E: он должен доказать локальное переключение центрального контекста, неизменность контекста остальных и `currentStep`, затем обновление общего контекста только после публикации. Отдельно проверяются `403` для кандидата, отсутствие общих управляющих элементов в preview и вид/текст тега. Для backend endpoint добавляются авторизационные и fallback-тесты.
