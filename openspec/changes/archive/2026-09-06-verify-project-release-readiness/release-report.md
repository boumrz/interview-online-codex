## Блокеры и наблюдения

### RELEASE-ACTIVITY-DURABILITY — блокирует выпуск

На полном контейнерном стенде тест десяти участников завершился `TIMEOUT: all captured sources acknowledged and durable`. Семь кандидатов выполнили два раунда по 100 нажатий: ожидалось 1400 событий. В PostgreSQL осталось 1399 строк с 1399 уникальными source ID; у первого кандидата 199 вместо 200, у остальных по 200. Повторный read-only срез через несколько минут показывает тот же результат. Ошибок nginx и HTTP5xx в этом прогоне нет.

Источник: `output/playwright/multi-activity/1788725641308/report.json`, `output/release-audit/multi-durable-counts.json`. Есть 1400 диагностических записей о получении успешных заголовков key_press. **Это не доказательство 1400 разных подтверждённых UUID:** ранний выход теста не сохранил полную карту action/ACK. Подтверждены недостающие durable-данные сценария; точная потерянная операция и причина требуют отдельного воспроизведения.

Независимый review указал возможную гонку при замене SSE-соединения: после проверки connectionId обработчик повторно ищет participant и может вернуться без сохранения. Это гипотеза по `CollaborationService.kt:440,1657`, а не установленная причина этого запуска. Условие снятия блокера: отдельный тест с точными UUID запросов/ACK и заменой соединения, исправление причины, полный неизменённый сценарий 2100 событий плюс равенство всех редакторов на здоровом стенде.

### RELEASE-ADMIN-REGISTRATION — блокирует выпуск, подтверждён кодом

Публичная регистрация назначает роль администратора по специальному nickname, сравнивая его без учёта регистра. Поиск/ограничение уникальности обычного nickname регистрозависимы. Это оставляет путь к административной роли при первичной регистрации или свободном варианте регистра существующего имени. Защита основной административной записи также распространяется на такие варианты.

Источники: `backend/src/main/kotlin/com/interviewonline/service/AuthService.kt:45,48`, `repository/UserRepository.kt:7`, `db/migration/V1__init.sql:16`, `service/AdminUserService.kt:49`. Требуется убрать назначение привилегий из публичного выбора имени и проверить защищённое provisioning/регистровые варианты отрицательными тестами. Runtime-воспроизведение уязвимости в этом аудите не выполнено.

### RELEASE-FAULT-CONTROL — блокирует выпуск, подтверждён кодом

Изменение настроек искусственной задержки/потери realtime-событий требует только действующего аккаунта. Сервер не проверяет административные полномочия или принадлежность к целевой комнате. Эти маршруты не отключены production-профилем; скрытие Agent Ops в интерфейсе не защищает API. Посторонний пользователь, знающий приглашение комнаты, может влиять на её realtime-доставку.

Источники: `backend/src/main/kotlin/com/interviewonline/controller/AgentController.kt:153,175,185`, `service/RealtimeFaultInjectionService.kt:17`, `frontend/nginx.docker.ssl.conf:89`. Условие выпуска: выключенный по умолчанию production-доступ к fault controls и серверная проверка полномочий при разрешённом включении. Runtime-воспроизведение уязвимости не выполнено.

### RELEASE-AUTH-NAVIGATION — повторяемый функциональный дефект

`e2e-task-create-language-default` дважды упал до проверки языка, а диагностическая копия с теми же действиями снова оказалась на `/login`. Регистрация отвечает 200, затем запрос `/api/me/profile` отменяется при немедленной полной навигации из уже видимого `/dashboard/rooms` в `/dashboard/tasks?lang=python`. JS-ошибок нет; кнопка создания задачи в актуальном коде существует и не скрыта ролью.

Диагностика: `task-language-diagnostic.json/.png/.log`. `LoginPage.tsx:68,116–125` допускает Navigate сразу после установки токена, до окончания получения профиля; catch ошибки профиля вызывает clearAuth, который удаляет токен синхронно (`authSlice.ts:58–63`). Дополнительный диагностический запуск сохранил последовательность без значений секретов: setAuthToken записывает токен; через 8ms clearAuth удаляет его уже на `/dashboard/rooms`; новый документ `/dashboard/tasks` через 6ms стартует без токена и возвращается на `/login` (`auth-navigation-diagnostic.json`). Удаление токена подтверждено наблюдением. Сам unmount lazy RTK query не вызывает abort, поэтому нельзя приписывать отмену только Navigate. Требуется отдельно закрыть сценарий быстрого reload/navigation после успешной регистрации, сохранив исходный тест без обхода дополнительным ожиданием профиля.

## Что требуется до выпуска

1. Устранить причину недостающей записи истории и подтвердить точные UUID/ACK при reconnect; повторить полный десятиучастниковый сценарий без ослабления 2100-event и editor-equality assertions.
2. Закрыть публичное назначение административной роли и доступ к fault controls, добавить отрицательные серверные тесты; проверить отзыв приватного realtime-доступа во время отложенной доставки.
3. Исправить раннюю навигацию/очистку сессии при регистрации; исходный language-default сценарий должен пройти.
4. Проверить реальные настройки доменов и TLS, разобрать отмеченные нестабильные тесты и провести повторную release-серию на стенде, соответствующем целевой архитектуре сервера.

До выполнения этих условий решение остаётся **NO-GO**.
