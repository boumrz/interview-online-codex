# Как писать и использовать спецификации InterHub

Спецификация — актуальный договор о наблюдаемом поведении продукта. Разработчик
должен понять результат реализации, а проверяющий — способ подтвердить его,
не придумывая продуктовых решений. Этот стандарт дополняет [AGENTS.md](../AGENTS.md).

## Где искать информацию

| Материал | Назначение | Когда читать |
| --- | --- | --- |
| [SPEC.md](../SPEC.md) | Фичи, порядок работ и краткий статус | В начале задачи |
| `features/<feature>.md` | Текущее поведение, требования и приёмка | Для затронутой фичи |
| [Шаблон](templates/feature.md) | Основа новой спецификации | При новой фиче |
| `references/` | Отчёты проверок, вложения и прежние редакции | Для конкретного вопроса |
| `openspec/` | Исторический архив | Когда нужна история решения |

Текст спеки редактируется напрямую. Отдельный журнал решений, генератор,
OpenSpec/BMAD, PRD, файл задач и Linear не обязательны. Вспомогательный документ
нужен только когда он снимает конкретную сложность; его назначение должно быть
понятно по ссылке из основной спеки.

## Глубина по риску

| Работа | Достаточная подготовка | Проверка |
| --- | --- | --- |
| Небольшое исправление | Изменить затронутое требование/сценарий; обозначить границы | Подходящий тест до кода и целевая регрессия |
| Обычная фича | Короткий договор по шаблону; отдельный проход полноты до кода | Приёмочные сценарии по реальному пути пользователя |
| Права, приглашения, приватные данные, realtime, миграции | Применимые роли/переходы/инварианты, ошибки и гонки; небольшой технический план при необходимости | Серверные интеграции и независимый обзор существенных изменений безопасности/надёжности |
| Документация/планирование | Сохранность требований и согласованность ссылок/статусов | Проверка документов; тесты приложения не нужны |

Размер и число файлов сами по себе не определяют риск. Для обычной фичи
ориентир — 1–3 страницы; сложную матрицу прав нельзя урезать ради лимита.
Первый экран отвечает: кто, что получит, какие границы и что осталось сделать.
Планируйте крупную работу небольшими законченными пользовательскими сценариями.
Отдельная архитектура нужна при изменении границ системы, а не для каждой кнопки.

## Содержание договора

1. **Результат и границы.** Пользовательская цель, текущий scope и явные исключения.
2. **Сценарии.** Исходное состояние → действие → наблюдаемый результат. Применимые
   загрузка, пустота, ошибка, отмена, повтор, возврат фокуса и сохранение черновика.
3. **Права и данные.** Кто читает/меняет данные; что сохраняется и удаляется;
   что происходит при смене аккаунта, команды или доступа.
4. **Требования и приёмка.** `R-01` описывает одно правило; `AC-01` задаёт проверяемый
   пример этого правила. Номер стабилен внутри фичи; удалённые IDs не использовать заново.
5. **Особые случаи и инварианты.** Только применимые конкуренция, повторы,
   устаревшие ответы, offline/reconnect, snapshots, отзыв прав и совместимость.
6. **Реализация.** Только контракты API, зависимости, миграции и ограничения,
   которые меняют решение исполнителя. Не пересказывать исходники.
7. **Вопросы и предположения.** Отличать подтверждённое решение от допущения.
   Блокирующие вопросы закрыть до зависящей от них реализации.
8. **Проверка и статус.** Сценарий → подходящая проверка, краткий результат,
   существенные ограничения и ссылка на подробный отчёт, если он нужен.

Неприменимые разделы можно опустить. Для маленькой правки не нужно переписывать
всю фичу. Таблицы прав и переходов удобнее длинного списка исключений. Термины
«snapshot», «revision», «ACK» объяснить при первом употреблении, если они нужны
для понимания поведения; пользовательские сценарии писать языком продукта.

Например, «reconnect работает» недостаточно. Проверяемый сценарий:
«После восстановления соединения сохранённые сообщения видны без дублей,
неотправленный черновик остаётся в поле; позднее подтверждение после отзыва
доступа не возвращает защищённые данные». Если нужна точная граница времени,
она должна быть отдельным согласованным требованием, а не догадкой исполнителя.

## Короткая проверка перед кодом

Автор делает отдельный проход после подготовки договора; дополнительный агент
для обычной задачи не обязателен. Для каждого применимого пункта есть ответ:

- Понятны актор, исходное состояние, действие и видимый результат?
- Границы и исключения не позволяют случайно расширить задачу?
- Успех, ошибка и восстановление описаны так, что их можно проверить?
- Права проверяются сервером; приватные данные не раскрываются сменой контекста?
- Для realtime/миграций разобраны повторы, гонки, устаревшие состояния и восстановление?
- Решения не противоречат связанным фичам, текущим указаниям пользователя и контрактам?
- При сокращении сохранилось каждое условие, которое меняет поведение или проверку?
- Есть подходящая проверка и нет нерешённых вопросов, меняющих результат или безопасность?

Результат прохода — исправленный договор и оставшиеся конкретные вопросы,
а не отдельный формальный отчёт. Неполноту, которую можно установить по коду,
проверкам и принятому контексту, сначала исследуют; пользователя спрашивают
только о реальном выборе. Не превращать каждое допущение о косметике в остановку.

## Реализация и доказательства

Для исполнимого поведения сначала написать/обновить наиболее подходящую проверку
и, когда практически возможно, подтвердить отказ из-за недостающего поведения.
Сломанная среда не доказывает RED. Для пользовательского потока предпочитать E2E
с реальными API; права, сохранение, миграции и гонки проверять backend integration
на PostgreSQL. Изолированную логику/взаимодействие можно проверить unit/component
тестом; если он заменяет потоковую E2E, кратко объяснить достаточность выбора.

Запускать проверки изменённого поведения и его существенных зависимостей.
Полная матрица, все уровни тестов, mutation testing и повторные обзоры не нужны
автоматически. Расширять проверку при новой правке, отказе или неразрешённом риске.
Тесты по наличию строк в исходниках не заменяют проверку поведения.

Независимый обзор обязателен перед выпуском существенных изменений auth,
ownership, приглашений, приватных данных, realtime authority, миграций данных
и изоляции исполнения. Его вход — изменённые требования, реализация, подходящие
проверки и конкретный риск. Блокирующие замечания закрываются до выпуска.
Других специалистов привлекать для конкретной задачи, без обязательной цепочки ролей.

Отчёт различает **план проверки**, **результат прежнего запуска** и **проверку
этой правки**. Старый PASS нельзя объявлять свежим результатом. Достаточно
связки `AC → тест/демонстрация → результат/ограничение`; детальное evidence
выносится в `references/` только когда оно действительно нужно.

## Поддержание актуальности

- Изменённое решение заменить в исходном разделе. Не оставлять отменённое
  правило рядом с новым и не заставлять читателя выбирать по дате.
- У каждого общего правила один владелец. Например, TEAM admission — P1.5,
  внешние назначения — P2.3, жизненный цикл членства — P3.1. В других фичах
  использовать точную ссылку; при изменении проверить затронутые зависимости.
- Историю хранит Git. Если исходный договор ещё не закоммичен либо его проверку
  нужно сохранить, перенести редакцию в `references/history/` с явной пометкой
  «история, не действующие требования». В активной спеке оставить существенное
  обоснование и короткую ссылку.
- Обновлять статус в начале фичи и краткую строку в `SPEC.md`. При снятии scope
  убрать его из действующих сценариев выпуска, сохранив исторические результаты.
- Существующие спеки приводить к стандарту при работе с ними; полезные детали
  сложных фич сохранять, не проводить массовое косметическое переписывание.

Статусы: **черновик** — существенные вопросы открыты; **готова к разработке** —
договор проверяем и блокирующие вопросы закрыты; **частично реализована** —
есть конкретный остаток; **реализована** — scope выполнен с указанными проверками
и ограничениями; **принята** — требуемые техническая и, когда предусмотрена,
продуктовая приёмки завершены; **снята с продукта** — только исторический материал.
Нужную продуктовую приёмку не подменять зелёными тестами.

## Стоимость работы

Обычная задача загружает индекс, нужную фичу и применимые общие правила.
Большие отчёты, все role prompts и архив не загружаются «на всякий случай».
Передача агенту содержит цель, конкретные R/AC, ownership и нужные ссылки;
ответ — краткий результат и доказательства. Linear обновляется при привязанной
задаче, машинный формат используется при реальном потребителе.

После 5–10 сопоставимых задач полезно сравнить общие токены/затраты до приёмки,
время, число уточнений и дефектов после просмотра. Учёт добровольный: отдельная
инфраструктура и отчёт на каждый шаг ради измерения экономии не нужны.
