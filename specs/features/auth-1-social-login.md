# AUTH.1 — Вход в InterHub через GitHub

GitHub — единственный внешний способ входа. Он доступен вместе с входом по нику и паролю. Гостевое участие в интервью остаётся доступным. Через GitHub можно открыть прежний кабинет, вернуться к интервью или продолжить вступление в команду.

Вход через Google снят с выпуска по решению владельца от 21 ноября 2026 года. Вход через GitHub уже работает на основном домене. [Инструкция по выкладке](../../DEPLOY_INTERHUB_RU.md)

## Пользовательские сценарии

| Ситуация | Действие пользователя | Результат |
| --- | --- | --- |
| Гость на главной | Нажимает «Войти» | На одном экране видны форма ника и пароля, кнопка «Войти через GitHub» при полной паре ключей. Кнопка доступна и при регистрации. Гостевое создание комнаты и вход по коду остаются прямыми. [Гостевая главная в UI.3](ui-3-interactive-learning.md) |
| Входит впервые | Выбирает провайдера, подтверждает вход, выбирает «Создать аккаунт» | На одном экране указывает ник и отображаемое имя. Имя можно исправить. Пароль InterHub для этого способа не требуется. Выбор «Я нанимающий» соответствует обычной регистрации. |
| Уже есть аккаунт с паролем | После первого возврата от провайдера выбирает «У меня есть аккаунт» и вводит прежние ник и пароль | Новый способ входа привязан к существующему пользователю. Его комнаты, задачи, команды, назначения и профиль сохраняются. Второй аккаунт не создаётся. |
| Уже входил этим способом | Ещё раз нажимает кнопку того же провайдера | Открывается прежний аккаунт без повторного выбора ника, даже после смены имени пользователя GitHub. |
| Уже авторизован, в том числе через GitHub без пароля | В профиле открывает «Способы входа», видит статус GitHub и при отсутствии связи нажимает «Подключить GitHub» и подтверждает его у провайдера | Возвращается в собственный профиль, выбранный сервис отмечен как привязанный. ID, данные и текущая сессия InterHub сохранены. |
| Отказал в доступе или произошёл сбой у провайдера | Возвращается ко входу | При возврате с отменой видит «Вход отменён», при временной ошибке — действие «Попробовать снова». Ник и пароль доступны независимо от состояния внешнего сервиса. При закрытии вкладки возврата от провайдера нет. На следующем открытии InterHub можно начать заново. |

## Требования и права

- **R-01. Доступные способы.** Сервер публикует `github` по наличию `GITHUB_CLIENT_ID` и `GITHUB_CLIENT_SECRET`. Неполная пара оставляет способ недоступным. При запуске сервер сообщает имя недостающей настройки без значения. Вход по паролю продолжается. Недоступный GitHub скрыт на входе, попытки входа и подключения отклоняются. Отвязка существующей связи регулируется R-16. На главной достаточно одной ссылки «Войти». На странице входа кнопка содержит название и знак GitHub, доступна с клавиатуры и сохраняет контраст в обеих темах. При ожидании ответа форма показывает прогресс и защищает от повтора. [Знак GitHub](https://brand.github.com/foundations/logo)
- **R-02. Подтверждение личности.** GitHub использует серверный обмен одноразового кода, PKCE S256, случайный `state` и подтверждение того же браузера через HttpOnly-cookie с SameSite=Lax и Secure на HTTPS. Сервер получает профиль владельца токена через `GET /user`. Пустой либо некорректный идентификатор даёт отказ без создания учётной записи. [Авторизация GitHub](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps)
- **R-03. Один владелец привязки.** Устойчивая пара для GitHub — `github + id` из подтверждённого профиля. Ник, имя, публичный или подтверждённый email могут совпасть у разных записей. Слияние по ним запрещено. При привязке со страницы входа пользователь явно выбирает это действие и подтверждает действующим паролем InterHub. Авторизованный пользователь подключает сервис из своего профиля по R-14–R-15, без выхода и без требования локального пароля. Новая привязка из профиля или со страницы входа занимает одно место GitHub: повтор той же identity идемпотентен, другая identity при уже занятом провайдере отклоняется без замены. Исторические несколько identities одного провайдера сохраняются и по-прежнему позволяют войти. Гонка запросов, занятая привязка или неверный пароль сохраняют исходного владельца и его данные. [Устойчивый идентификатор GitHub](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/best-practices-for-creating-an-oauth-app)
- **R-04. Первый профиль и совместимость.** Новый ник уникален, 3–32 печатных ASCII-символа без пробелов, по действующим правилам InterHub. Разрешено отображаемое имя Unicode длиной 2–64 символа. Если публичное имя отсутствует, поле заполняет пользователь. Занятый или зарезервированный администраторский ник можно исправить в форме. Сервер создаёт обычную роль `user`, личный банк задач и сессию. Внешний аккаунт или отметка «Я нанимающий» сами по себе не предоставляют администрирование, командное членство или права в комнате. Для нового профиля с внешним входом локальный пароль отсутствует. Для старых аккаунтов локальный вход и привязка принимают прежние точные credentials, включая ранее допустимую кириллицу. [UI.2, правило регистрации R-27](ui-2-usability-theme-polish.md)
- **R-05. Жизненный цикл попытки.** Сохранить действующий предел в 10 минут. Callback атомарно занимает попытку до обмена у провайдера. Завершение или привязка меняют аккаунт однократно. Исправимый отказ формы допускает повтор в оставшееся время. После сбоя обмена или истечения срока предлагается новый вход. Чужой браузер, другой провайдер, повторный callback и запоздавший ответ старой попытки не публикуют сессию. Временные записи очищаются по истечении срока. При удалении пользователя удаляются его привязки.
- **R-06. Адреса и возврат.** Сервер проверяет точный origin на запросах начала, завершения и привязки. Внешние адреса авторизации и callback выбираются из доверенной конфигурации. Адрес InterHub задаётся на сервере, HTTPS обязателен вне локального loopback. Источник запроса, произвольный `next` или заголовки прокси не задают внешний адрес перехода. Возврат внутри InterHub описан в R-11.
- **R-07. Данные и сессия.** Минимум постоянных данных — провайдер, устойчивый внешний идентификатор, внутренний пользователь и время привязки. Код авторизации приходит только на серверный callback, который сразу переводит браузер на чистый экран завершения без кода и `state`. Ответы имеют `Cache-Control: no-store`, callback — `Referrer-Policy: no-referrer`. Секрет приложения и проверка токена остаются на сервере. Access-, refresh- и ID-токены провайдера не сохраняются и не попадают в браузер или аналитику. Временная запись хранит только нужные для попытки поля и хеши доказательств браузера и `state`. Прокси, серверные логи и Метрика не записывают query callback, токены и детали профиля. Интерфейс сохраняет обычную сессию InterHub только после успешного чтения `/me/profile`. При временном отказе чтения повторяет только этот шаг.
- **R-08. Ошибки и смена контекста.** Запросы имеют конечное время ожидания. Отмена, отказ провайдера, истечение и неисправность показываются понятным русским текстом. Введённые поля остаются доступны при исправимой ошибке. Уход со страницы, повторное нажатие, выход из аккаунта или вход другого пользователя в соседней вкладке не должны заменить новую сессию старым ответом. При недоступности GitHub сохраняется вход по нику и паролю.
- **R-09. Разрешения GitHub.** Для GitHub используется отдельный OAuth App только для входа, с пустым набором дополнительных разрешений. Единственный запрос данных о пользователе — `GET https://api.github.com/user`. Скрытая почта, отсутствие имени и переименование GitHub-логина совместимы со входом. Не обращаться к почте, репозиториям, организациям и членству. Выделенный клиент нужен в том числе потому, что GitHub может применить ранее выданные этому клиенту разрешения. Неожиданно расширенный набор — ошибка настройки, до выдачи сессии. [Разрешения GitHub](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/scopes-for-oauth-apps), [GitHub Users API](https://docs.github.com/en/rest/users/users#get-the-authenticated-user)
- **R-10. Доступность по конфигурации.** Интерфейс узнаёт доступность GitHub через `GET /providers`. Без полной пары список пуст, а вход и привязка отклоняются до обращения к GitHub или проверки пароля. Без активной попытки `/login/social` возвращает на `/login`. При полной паре действуют проверки origin, общего ключа попыток и доверенных адресов GitHub. Отсутствие пары блокирует незавершённые попытки GitHub. Старые настройки Google и VK игнорируются. Пользователи, привязки и существующие сессии InterHub сохраняются.
- **R-11. Куда вернётся пользователь.** Обычный вход ведёт в личный список интервью. Если пользователь уже выбрал вступление в команду, существующий путь `/join/team?resume=accept` продолжает именно это действие после повторной проверки действительности приглашения. Если человек сам выбрал авторизацию из комнаты, вернуть его в исходную комнату с новой проверкой доступа. При сохранении роли кандидата возврат ведёт прямо в рабочую комнату без элементов обучения по [UI.3](ui-3-interactive-learning.md). Закрытая или недоступная комната даёт штатное сообщение. Сервер связывает уже известную ему комнату с короткоживущей попыткой по внутреннему идентификатору. После подтверждения профиля клиент обращается к фиксированному адресу на том же сайте. Сервер однократно разрешает сохранённый контекст для завершённой попытки, того же браузера и выданной сессии. Контекст можно создать только при допустимом исходном входе в комнату. Произвольный внутренний ID не позволяет получить ссылку комнаты. При отсутствующем или просроченном контексте возврата из комнаты открывается личный кабинет с пояснением. Ссылки и токены приглашений, произвольный URL и данные кандидата не передаются провайдеру и не записываются в новое клиентское хранилище восстановления. Вход по гостевой ссылке без нажатия «Войти» не запускает авторизацию. [Командные приглашения](p0-1-team-invitations.md), [правила доступа в комнату](p2-3-room-assignments.md)

- **R-12. Публичные документы.** По решению владельца 18 ноября добавить страницы `/privacy` и `/terms`, доступные без входа при любой конфигурации провайдеров. Ссылки находятся на гостевой главной и экране входа. Документы ссылаются друг на друга и позволяют вернуться в приложение. Политика описывает фактические категории данных интервью, минимальные данные GitHub и хранение прежних связей, серверный прогресс обучения и Яндекс Метрику, способы обращения по данным и реальные ограничения удаления. Подтверждённые реквизиты оператора — **Желтов Роман Геннадьевич**, контакт **boumrz@gmail.com**. Не придумывать сроки хранения, географию серверов, юридический статус или автоматическое удаление.

- **R-13. Бесплатные интеграции.** По решению владельца вход и привязка используют прямой GitHub OAuth без платного посредника. Не подключать Identity Platform, платный тариф Firebase Authentication, Auth0, Clerk, платный Marketplace app или иной сервис с оплатой за пользователей/входы. Платёжный аккаунт и пробный платный период для этого сценария не требуются. Существующие расходы на сервер и домен InterHub остаются отдельными. Ограничения частоты запросов провайдеров обрабатываются штатной ошибкой с возможностью повторить вход; автоматически повышать тариф или включать оплату нельзя. [регистрация своего GitHub OAuth app](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/creating-an-oauth-app).

- **R-14. Способы входа в профиле.** Собственный профиль на `/profile` и в командном кабинете показывает раздел, если GitHub доступен или уже привязан. В разделе есть знак GitHub, статусы **«Привязан» / «Не привязан»** и действие **«Подключить GitHub»** при доступности подключения. Сервер отдаёт статусы владельцу с действующей сессией при любой конфигурации ключей. Недоступный провайдер сохраняет статус прежней связи. При ошибке чтения есть повтор. После подтверждения у провайдера пользователь возвращается в `/profile`. Успешный ответ обновляет статус без выхода и смены сессии. Ошибка, отмена и истечение попытки объясняются в профиле, позволяют начать заново и не повреждают данные. Доступны клавиатура, обе темы, desktop/tablet и понятное состояние ожидания. Показывать только факт связи и доступность операций.
- **R-15. Безопасная привязка из профиля.** Начало — явный POST с текущей действующей сессией и точным Origin. Попытка `PROFILE_LINK` связывается на сервере с исходным user ID, хешем именно этой сессии и прежним доказательством браузера; срок, state, PKCE и проверка GitHub остаются по R-02–R-07. Callback только подтверждает внешнюю личность и возвращает на фиксированный профиль с безопасным маркером продолжения; связь создаёт последующий POST с той же действующей сессией, cookie и Origin. Нельзя завершить такую попытку login/register/password-link endpoint или наоборот. Завершение не создаёт пользователя/сессию, не выдаёт новый токен и не меняет права. Другая личность провайдера, уже занятая другим пользователем, даёт конфликт без переноса связи и раскрытия владельца. Повтор или гонка не создаёт дубликат; та же identity того же пользователя допустима как повторный результат. Подключённый провайдер не заменяется другим аккаунтом через этот интерфейс; конкурирующие добавления из профиля и через прежний password-link сериализуются по пользователю с единым порядком блокировок. Исторические несколько identities одного провайдера сохраняются до явной отвязки. Статус означает наличие хотя бы одной связи. Отмена, просроченная попытка, отсутствие/смена сессии и удаление пользователя исключают новое завершение. При выходе или смене аккаунта в браузере клиент прекращает ещё не отправленное завершение, а поздний ответ не восстанавливает сессию и не меняет интерфейс нового пользователя. Существующий logout остаётся клиентским: уже отправленная авторизованная операция может завершиться для исходного пользователя, но никогда не переключает аккаунт. Новые секреты не сохраняются в клиентское recovery-хранилище. Для замены сначала выполнить отвязку по R-16, затем начать новое подключение.

- **R-16. Отвязка способа входа.** В собственном профиле доступно явное подтверждение отвязки подключённого GitHub, включая провайдера без действующей конфигурации. Если пароля InterHub ещё нет, диалог требует задать и повторить его. Новый пароль соответствует правилам регистрации и пределу BCrypt 72 символа. Сервер проверяет точный Origin и действующую сессию владельца. Сохранение хеша первого пароля и удаление всех связей выбранного провайдера проходят в одной транзакции. Неполный запрос, ошибка пароля и отказ в доступе оставляют привязку на месте. Существующий пароль сохраняется. Если параллельная операция опередила установку пароля при отвязке другого провайдера, пользователь подтверждает отвязку заново с учётом актуального состояния. Параллельные изменения способов входа одного пользователя сериализуются. Аккаунт, данные и выданные сессии InterHub сохраняются. Ранее начатые подключения этого провайдера из профиля отменяются. Если отвязка завершается первой, параллельный вход повторно проверяет исходную связь и не выдаёт новую сессию. Если внешний аккаунт привязан к другому профилю InterHub, сначала нужна явная отвязка из того профиля. Пароль не сохраняется в клиентское recovery-хранилище и не попадает в ответы и журналы. Перенос данных между профилями отсутствует.

- **R-17. Совместимость после отключения Google.** Прямые запросы на вход, callback, подключение и отвязку через Google отклоняются как запросы к неподдерживаемому провайдеру. Незавершённые попытки Google нельзя использовать для выдачи сессии и привязки, а ранее завершённые — для продолжения возврата в комнату. Исторические записи остаются в базе и не показываются как способ входа. Они не считаются действующей альтернативой GitHub или паролю. Существующие аккаунты, данные и сессии InterHub сохраняются. Пользователь с действующей сессией может подключить GitHub к своему профилю. Для нового входа нужен уже привязанный GitHub или пароль InterHub. Ранее применённые миграции Flyway сохраняются.

| Область | Текущий контракт реализации |
| --- | --- |
| Провайдеры и попытка входа | Под `/api/auth/social` работают `GET /providers`, `POST /{provider}/start`, `GET /{provider}/callback`, `GET /pending`, `POST /complete`, `POST /link`. Доступен `github`. Для GitHub выполняется обмен кода, проверка пустого набора дополнительных разрешений и `GET https://api.github.com/user`. Старые записи Google и VK сохраняются по R-17. При конкурирующей регистрации или привязке конфликт обрабатывается в транзакции и возвращает безопасный ответ. Поля внешнего профиля и ник не должны появляться в SQL-диагностике конфликта. Новый социальный профиль получает `role=user`, выбранный `isHr`, пустой пароль и личный банк по действующим правилам. [Хранение](../../backend/src/main/kotlin/com/interviewonline/features/socialauth/SocialAuthPersistence.kt), [сервис](../../backend/src/main/kotlin/com/interviewonline/features/socialauth/SocialAuthService.kt) |
| Подключение из профиля | `GET /connections` (Bearer) возвращает `{connections:[{provider,linked,available}]}` для GitHub. `POST /{provider}/profile-link/start` (Bearer + Origin) начинает `PROFILE_LINK` и возвращает обычный `authorizationUrl`. `POST /profile-link/complete` (Bearer + Origin + cookie) подтверждает связь, возвращая `{provider,linked:true}` без токена сессии. Callback возвращает `/profile?social_link=ready` либо безопасную категорию ошибки. Совместимая [V45](../../backend/src/main/resources/db/migration/V45__social_auth_profile_link.sql) добавляет `intent` с default `login` и серверные initiating user/session-hash; старые identities и flows сохраняются. |
| Возврат из комнаты | Гость может выбрать вход через аккаунт прямо из диалога ввода имени. До подключения `POST /room-context` принимает `inviteCode` действующей гостевой ссылки в теле запроса к InterHub. Сервер проверяет обычный доступ гостя к комнате. Для участника с подключением поддерживаются внутренний `roomId` и действующий `X-Room-Event-Token` именно этой комнаты. Сервер устанавливает HttpOnly-cookie и возвращает публичный `contextId`. `POST /{provider}/start` с `roomReturn=true` переносит контекст только если `roomContextId` этой вкладки соответствует действующей cookie. Успешный `complete` или `link` связывает попытку с хешем выданной сессии. После чтения `/me/profile` клиент вызывает `POST /continue` с этой сессией и cookie. Сервер однократно возвращает разрешённый путь и очищает cookie. Если контекст создать или применить не удалось, вход открывает кабинет с пояснением и без автоматического предложения обучения. [Контроллер](../../backend/src/main/kotlin/com/interviewonline/features/socialauth/SocialAuthController.kt) |
| Миграция и данные возврата | V43 добавляет совместимые поля для признака возврата, внутренних ID комнаты/команды, хеша ссылки и хеша выданной сессии. Поля комнаты допускают `NULL`, удаление комнаты очищает ссылку на неё. Срок временной записи остаётся 10 минут. После использования данные возврата очищаются. Секреты приглашения и провайдерские токены в этих полях отсутствуют. [V43](../../backend/src/main/resources/db/migration/V43__social_auth_room_return.sql), [исходная V34](../../backend/src/main/resources/db/migration/V34__social_auth.sql) |
| Интерфейс и журналирование | Кнопка GitHub использует локальный знак. Адрес провайдера проверяется перед переходом. Сессия публикуется после успешного чтения профиля. Разрешённый путь фиксируется до публикации сессии, чтобы повторный рендер не заменил возврат в комнату переходом в кабинет. При недоступном контексте автоматическое предложение обучения на странице возврата подавлено. Оба прокси приложения исключают OAuth callback, включая запоздавшие запросы к отключённым провайдерам, из журналирования запроса. Внешний входной прокси целевой среды требует отдельной проверки перед выпуском. [Экран возврата](../../frontend/src/pages/SocialLoginPage.tsx), [HTTPS](../../frontend/nginx.docker.ssl.conf), [HTTP](../../frontend/nginx.docker.http.conf) |

В `GET /api/auth/social/connections` и в ответе успешного `POST /api/auth/social/{provider}/unlink` каждая строка содержит `provider`, `linked`, `available`, `canUnlink`, `requiresPassword`. Для подключённого провайдера `canUnlink` означает отвязку с уже существующим паролем, а `requiresPassword` — необходимость создать первый пароль. POST принимает необязательное тело с `newPassword`. Для связанного аккаунта без пароля запрос без `newPassword` возвращает 409 `SOCIAL_PASSWORD_REQUIRED`. Если пароль уже установлен и запрос отвязки существующей связи содержит новый, сервер возвращает 409 `SOCIAL_PASSWORD_ALREADY_SET`. Для уже отвязанной строки запрос без пароля или точный повтор пароля возвращает текущее состояние. Запрос с другим паролем возвращает 409 `SOCIAL_CONNECTION_CHANGED`.

`pending` возвращает только провайдера, предложенное имя и признак существующей привязки. Для уже привязанного пользователя `complete` принимает пустое тело, для нового — ник, имя и отметку нанимающего. Для `link` нужны ник и пароль прежнего аккаунта. Успех возвращает обычную `AuthResponse` InterHub. Командное приглашение продолжает существующий фиксированный путь `/join/team?resume=accept` и проверяется штатным механизмом приглашений.

Настройки сервера — `PUBLIC_BASE_URL`, `SOCIAL_AUTH_FLOW_SECRET`, `GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET`. Секреты находятся в защищённой конфигурации backend. Одна сборка frontend получает доступность из `GET /providers`. [Пример конфигурации](../../deploy/env/docker.env.example), [Docker Compose](../../docker-compose.prod.yml)

| AC-06 | R-04, R-08, R-09 | Пользователь GitHub со скрытой почтой и пустым именем вводит имя вручную. После изменения GitHub-логина попадает в тот же InterHub. Подтверждение у GitHub соответствует минимальному доступу. |

| AC-08 | R-06, R-07, R-11 | Браузерные проверки: вход с главной → личный кабинет; вход через аккаунт из диалога ввода имени до realtime-подключения → та же комната с действующими правами; продолжение принятия приглашения → ожидаемая команда. Отозванное приглашение или потеря доступа дают штатный отказ. При возврате от Google или GitHub участник, оставшийся кандидатом, видит только рабочий экран комнаты. Страницы остаются на своих адресах, содержат полные читаемые тексты, подтверждённые данные оператора, взаимные ссылки и возврат. Проверить мобильную ширину и обе темы. ## Внешние настройки и выпуск

Рабочий GitHub OAuth App использует callback `https://interview.vtools.tech/api/auth/social/github/callback`. Локальный callback для тестов — `http://localhost:5173/api/auth/social/github/callback`. Секрет хранится вне Git. Выкладку и живую проверку на основном домене выполняет владелец. [Инструкция](../../DEPLOY_INTERHUB_RU.md)
