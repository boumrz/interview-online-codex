# AUTH.1 — Вход через Google и VK

Статус: **сохранена как отключённая заготовка; интеграция отложена пользователем**.
Общий `FEATURE_SOCIAL_AUTH_ENABLED=false` выключает frontend и серверные
сценарии, даже при заданных настройках провайдеров. Продолжить интеграцию
только по новому запросу пользователя. [Прежние проверки реализации](../references/2026-10-05-social-login-verification.md)
сохраняются как evidence подготовки, а не включённого выпуска.

## Результат и границы

Сейчас пользователи сохраняют обычные вход и регистрацию по нику и паролю:
нет Google/VK кнопок, новых форм, ошибок, фоновых social requests и загрузки
брендовых assets. Прямой `/login/social` возвращает обычный `/login`.
Код, проверки и инструкция сохранены для будущего подключения.

Ниже описан подготовленный сценарий после явного будущего включения.
Пользователь входит через Google или VK ID, сохраняя обычный вход по нику и
паролю. «Gmail» означает аккаунт Google; чтение почты и отправка писем не нужны.
При первом входе пользователь выбирает ник и имя. Свой прежний аккаунт он
может явно привязать, подтвердив его ник и пароль, вместо создания нового.

В этом объёме нет восстановления пароля по email, автоматического объединения
аккаунтов, управления отвязкой провайдеров и установки локального пароля для
аккаунтов, созданных через провайдера. Их повторный вход проходит через того
же провайдера. Инструкция подключения: [настройка](../references/2026-10-05-social-login-setup.md).
Общие правила регистрации и старых credentials: [UI.2 R-27](ui-2-usability-theme-polish.md).

## Акторы и состояния

| Состояние | Действие | Результат |
| --- | --- | --- |
| Гость, провайдер настроен | Нажать Google/VK и подтвердить вход | Сервер проверяет личность; первый вход открывает короткую форму |
| Проверенная новая личность | Выбрать ник и имя | Создан обычный пользователь, его банк задач и новая сессия |
| Проверенная новая личность, есть локальный аккаунт | «У меня есть аккаунт», ввести его credentials | Явная привязка к прежнему пользователю; его данные и права сохранены |
| Проверенная ранее привязанная личность | Вернуться от провайдера | Подтверждение текущего профиля и вход в прежний аккаунт |
| Другой аккаунт вошёл, пока ответ ожидался | Приходит старый ответ | Старая попытка не меняет текущий аккаунт |
| Провайдер выключен/не настроен | Открыть вход | Его кнопка отсутствует; локальный вход доступен |
| Отмена, истёкший/чужой/повторный callback | Вернуться | Понятное сообщение и возможность начать вход заново, без новой привязки |

## Требования

- **R-01.** Сервер публикует только включённые, полностью настроенные
  провайдеры при включённом общем флаге R-10. По умолчанию все флаги выключены.
  Неполная включённая конфигурация
  не должна создавать работающую кнопку. Секреты находятся только на сервере.
- **R-02.** Authorization code обменивается сервером. Обе интеграции используют
  PKCE S256, случайный state и независимое доказательство того же браузера
  в HttpOnly cookie, SameSite=Lax, Secure на HTTPS. Google дополнительно
  проверяет nonce и подпись/issuer/audience/expiry ID token. VK сверяет
  state и серверный user_info с user_id ответа token endpoint.
- **R-03.** Личность определяется парой «провайдер, неизменяемый subject».
  Email, имя и ник не являются доказательством права на существующий аккаунт.
  Привязка требует явного действия и проверки локального пароля. Личность
  нельзя перепривязать к другому пользователю; конфликты и конкурентные
  запросы не создают дубликатов или смену владельца.
- **R-04.** Первый вход требует уникальный ник по текущим правилам новой
  регистрации, имя 2–64 символа и допускает выбор «Я нанимающий». Новая роль
  всегда `user`; ник первичного администратора недоступен. Локальный пароль
  у такого аккаунта отсутствует; обычный login с ним возвращает стандартный
  отказ. Существующие пароли, IDs, комнаты, задачи и членство не меняются.
- **R-05.** Временная попытка живёт 10 минут. Callback атомарно заявляет
  попытку один раз до сетевого обмена; completion/link также атомарны и
  одноразовы. Чужой браузер, другой провайдер, истечение и повтор отвергаются.
  Ошибка проверки профиля/занятый ник/неверный локальный пароль допускают
  исправление формы в пределах проверенной попытки. После сбоя обмена нужен
  новый вход. Истёкшие временные записи очищаются.
- **R-06.** API начала/завершения/привязки проверяет точный Origin настроенного
  приложения. Callback и авторизационный redirect фиксированы серверной
  конфигурацией, не берутся из Host, Forwarded или пользовательского next.
  Public base — один origin, HTTPS; локальный HTTP допускается для loopback.
- **R-07.** Доступ/refresh/ID tokens провайдеров не сохраняются в БД, браузере,
  URL, аналитике или логах. Браузер получает только безопасный статус/имя
  и обычную AuthResponse через защищённый POST. Callback немедленно уводит
  на `/login/social` без code/state/tokens. Cookie и ответы — no-store,
  callback — Referrer-Policy no-referrer. Доказательства browser/state в БД
  хешированы; verifier/nonce могут выводиться HMAC из отдельного серверного
  секрета. Обычная текущая сессия публикуется по существующей схеме хранения
  только после подтверждения `/me/profile`; неудачный ответ остаётся в памяти
  страницы и не попадает в recovery storage.
- **R-08.** Сетевые операции с провайдерами и клиентские запросы имеют конечный
  срок ожидания. Отмена, недоступность, ошибка сети и истечение показаны
  понятным русским текстом. Формы сохраняют ввод при исправимой ошибке;
  повтор/смена режима/уход/смена аккаунта не публикуют устаревший ответ.
- **R-09.** Google запрашивает только идентификационные scopes; VK — минимум
  для идентификации и имени. Никакой автоматической роли администратора,
  команды или доступа к чужим интервью провайдер не выдаёт.
- **R-10. Отложенная интеграция.** `FEATURE_SOCIAL_AUTH_ENABLED=false` — общий
  флаг backend и frontend build. При false LoginPage не монтирует social
  компонент и не загружает его стили/assets/список провайдеров;
  `/login/social` возвращает `/login` без social ошибки или формы. Backend
  публикует пустой список, отвергает start/pending/complete/link до чтения flow
  и credentials; callback возвращает `/login` без provider exchange.
  Неиспользуемая неверная social конфигурация не мешает startup. Provider
  flags и ключи сами по себе не включают модуль. Обычные регистрация, пароль,
  сессии и права не меняются. Будущее включение требует флага на обеих сторонах,
  пересборки/перезапуска frontend, инструкции и живой проверки.

## API

- `GET /api/auth/social/providers` → `{ providers: ("google" | "vk")[] }`.
- `POST /api/auth/social/{provider}/start` → `{ authorizationUrl: string }` и
  временная HttpOnly cookie. Клиент переходит по URL только ожидаемого
  HTTPS authorization endpoint выбранного провайдера.
- `GET /api/auth/social/{provider}/callback` — server code exchange и фиксированный
  redirect на `/login/social`; допускается только безопасный код результата.
- `GET /api/auth/social/pending` → `{ provider, displayName, accountExists }`.
- `POST /api/auth/social/complete` → существующая `AuthResponse`; для новой
  личности тело `{ nickname, displayName, isHr }`, для привязанной — `{}`.
- `POST /api/auth/social/link` → `AuthResponse`; тело `{ nickname, password }`.

Приложение использует один public origin и proxy `/api` к backend. Общий
произвольный return URL не добавляется. Возврат к уже сохранённому приглашению
может хранить только фиксированный путь `/join/team?resume=accept`, без токена.

## Приёмка и проверка

- **AC-01 (R-01/R-08).** Выключенные кнопки отсутствуют; настроенные видны;
  start network error позволяет повторить; неожиданный redirect отвергается.
- **AC-02 (R-02/R-05/R-06/R-07).** PostgreSQL + реальные HTTP fake-provider
  ответы проверяют правильный обмен, PKCE, browser/state binding, Origin,
  повтор/истечение, nonce и негативные Google claims, VK device_id/user_id.
- **AC-03 (R-03/R-04/R-05).** Новая регистрация/повторный вход дают тот же ID;
  занятый/кириллический/админский ник не создаёт аккаунт; явная локальная
  привязка сохраняет данные, неверный пароль/чужая привязка/гонка отвергаются.
- **AC-04 (R-04).** Flyway миграция с PostgreSQL сохраняет старый local login,
  включая кириллицу; social-only local login отказывает без исключения BCrypt.
- **AC-05 (R-07/R-08).** Браузер проверяет профиль до публикации сессии,
  повторяет hydration без повторной регистрации/привязки; уход, редактирование
  и смена аккаунта защищены; временные секреты не появляются в storage/URL.
- **AC-06 (R-08/R-09).** Отмена/недоступность/истечение возвращают понятный
  вход; пользовательские страницы не содержат технических идентификаторов.
- **AC-07 (R-10).** При false и даже доступных provider настройках/ответах нет
  кнопок, social requests/assets; прямой return открывает прежний login.
  Выключенный backend не активируется отдельным provider flag, не завершает
  старый flow и не проверяет пароль для привязки; неисправные неиспользуемые
  настройки не ломают startup. Прежние регистрация/вход проходят свои проверки.

Независимый scoped security/reliability review обязателен перед включением.
Проверки без реальных внешних ключей не подтверждают окончательную настройку
кабинетов, публикацию consent screen и вход живым Google/VK аккаунтом.

Техническая проверка пройдена: backend 18 PostgreSQL + 4 configuration tests,
12 social browser сценариев + 11 сценариев прежней авторизации, typecheck и
production build. Найденные deadline/pagehide/terminal retry замечания закрыты
с отдельным RED→GREEN; [подробные результаты](../references/2026-10-05-social-login-verification.md).
Модуль отложен и выключен общим флагом; live credentials, целевой Nginx и живой
вход проверяет владелец после возобновления интеграции.

Текущее отключение R-10/AC-07 подтверждено: 32 backend проверки
(24 PostgreSQL + 8 configuration), 14 browser проверок, typecheck и production
build; обычный login дополнительно проверен на работающем dev server без
перезапуска. Независимый scoped review не выявил блокирующих замечаний.
[Проверка заготовки](../references/2026-10-05-social-login-deferred.md).
