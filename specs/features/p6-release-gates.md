# P6 — финальный выпуск

Статус: реализация доступна для локального просмотра; продуктовая приёмка ожидается.
Актуализировано: 2026-10-04. Результат: выпустить текущий состав продукта с
подтверждёнными правами, сохранением данных и применимыми пользовательскими потоками.

## Текущий scope

Действующие фичи перечислены в [SPEC.md](../../SPEC.md). Сквозной сценарий:
приглашение → трек/вакансия → библиотека/набор → программа → создание интервью →
комната → результат и экспорт. Free/taskless интервью остаются отдельными
допустимыми путями. Новые объединения команд, аудит в UI и новые приостановки
сняты с продукта; они не являются обязательным release flow. Исторические
переадресации объединённых команд и данные сохраняются по P5.2/P5.3.

## Требования и выпускные проверки

- **R-01. Пользовательские пути:** актуальные R/AC фич покрывают основной путь,
  допустимые роли, ошибки/retry, отзыв прав и сохранение после reload. Нет
  ожиданий отменённых экранов/действий; готовность проверяется по текущим спекам.
- **R-02. Данные:** миграции проверяются на fresh install и upgrade с существующими
  TEAM rows на PostgreSQL. Командные пространства выпускаются без feature flag
  по [P0.2 R-11](p0-2-workspace-navigation.md), с обязательными стабильными ключами
  по [P0.1 R-08](p0-1-team-invitations.md). Существующие данные и права сохраняются.
  Другие действующие flags не включаются автоматически этим решением.
- **R-03. Безопасность:** нет открытых P0/P1 security blockers; существенные
  auth/authority/realtime/migration изменения проходят независимый обзор.
  Evidence использует синтетические данные и не содержит секретов/кандидатской PII.
- **R-04. Realtime topology:** несколько backend-процессов требуют маршрутизации
  одной комнаты к одному realtime-хосту либо принятого межпроцессного транспорта
  событий. Общая PostgreSQL сама не доставляет editor/SSE события между процессами.
  Приёмка topology включает применимые нагрузочные/конкурентные проверки;
  полный load suite не становится обязательным для каждой обычной правки.
  При однопроцессном локальном просмотре это не дополнительный блокер разработки.
- **R-05. Приёмка:** техническая проверка и продуктовый просмотр различаются.
  Ограничения/непройденные проверки записаны явно; исторический PASS не является
  доказательством текущего полного suite. Тестовые fixtures закрывают свои browser/context
  при ошибке setup и явно проверяют готовность нужного интерфейса без ожидания фоновых
  ресурсов или увеличения общего timeout. Новые перезапуски/выкладка требуют
  соответствующего указания пользователя, не выполняются ради документационного gate.
- **R-06. Диагностический скрипт:** проверка окружения обращается к защищённому
  endpoint с токеном, явно переданным через `INTERHUB_AUTH_TOKEN`. Без токена
  запрос не выполняется и выводится понятная ошибка. Токен не попадает в URL,
  аргументы дочернего процесса или журнал. HTTP/JSON ошибки, отсутствующий либо
  неизвестный статус и результат FAIL не выдаются за успех; PASS/WARN различаются.
- **R-07. Локальная среда разработки:** обновления зависимостей сохраняют
  пользовательские сценарии, API proxy и доставку SSE с освобождением upstream
  после закрытия клиента. Неиспользуемые служебные HTTP-действия dev-сервера
  открытия редактора и принудительной перекомпиляции отключены; ресурсы получают
  `Cross-Origin-Resource-Policy: same-origin`. Проверка опубликованных advisories
  дополняется проверкой фактического HTTP-поведения и независимым обзором защиты.
  Диагностические сообщения dev-сервера не сохраняют токены и личные query
  параметры подключений, в том числе во время первичной компиляции или ошибки
  обработки пути; реальные ошибки компиляции остаются видимыми.
- **R-08. Изоляция тестовых данных:** E2E, которые регистрируют аккаунты или
  изменяют серверные данные, запускаются с собственным API и временной
  PostgreSQL-схемой. Прямой запуск файла защищён тем же общим guard, что
  запуск из package scripts. До fixtures и изменений проверяется идентичность
  изолированного API и его frontend proxy; основная локальная БД, обычные
  порты 8080/5173, удалённый адрес или отсутствующее подтверждение не допускаются.
  Необходимо проверять фактическую схему, а не доверять одному флагу окружения.
  Read-only подтверждение изоляции доступно только в test runtime, не в
  production приложении; оно не раскрывает пароли, JDBC credentials и токены.
  Обычные команды E2E запускают изолированное окружение. После успеха или ошибки
  runner закрывает свои процессы и удаляет свою временную схему.
  Проверки без изменения данных и под собственными fake HTTP fixtures
  сохраняют возможность отдельного запуска без обращения к рабочей базе.
