# Markdown: причины потери ввода и проверка исправления

Дата проверки: 2026-10-02. Контракт: [P2.1, R-02–R-05 и AC-02–AC-07](../features/p2-1-room-layout-modes.md),
для ожидающего кода после завершения — [P3.3, R-02–R-03 и AC-05](../features/p3-3-interview-result.md).
Проверка выполнена на отдельном frontend `15173` и backend `18080` с PostgreSQL
и синтетическими аккаунтами. Пользовательский сервер `8080` не перезапускался.
Это техническая проверка описанных сценариев; пользовательская приёмка остаётся отдельной.

## Установленные причины

1. **Непрерывный ввод откладывал отправку без ограничения.** Каждая клавиша
   перезапускала только trailing debounce. При быстром вводе сохранение могло
   долго не начинаться. Добавлена отправка последнего значения не реже чем через
   750 мс, наряду с debounce 160 мс после паузы.
2. **Зависший POST удерживал общую очередь.** У запроса мутации не было конечного
   срока ожидания: последующие сохранения оставались за ним. Добавлен предел
   10 секунд, отмена запроса и восстановление доставки с прежним намерением.
   Неотправленные значения одного поля одной задачи объединяются; уже начатая
   попытка сохраняет свою идентичность. Очередь активности кандидата остаётся отдельной.
3. **Локальная версия приватного условия расходилась с серверной.** UI повышал
   optimistic revision на каждую клавишу, хотя сервер применяет сравнение версий
   на фактически принятую запись. Отказ предыдущей записи делал последующие версии
   неверными, а серверное состояние заменяло локальный черновик. Теперь отправка
   использует последнюю серверную версию; неподтверждённый текст переносится через
   внешние правки и повторяется после конфликта.
4. **HTTP 409 и SSE могли приходить в обратном порядке.** Если отказ версии уже
   пришёл, но новая версия ещё не дошла по SSE, намерение ранее исчезало из очереди.
   Оно теперь ожидает актуального приватного состояния. Повтор получает новую
   последовательность в конце очереди, чтобы не обесценить уже ожидающий код или заметку.
5. **Возврат к старому серверному тексту ошибочно снимал dirty до отправки.**
   Воспроизведено: значение B ожидает ответа, пользователь возвращает BASE до
   окончания debounce; сравнение с прежним canonical BASE снимало dirty, после
   чего подтверждение B заменяло новый ввод. Теперь совпадение не снимает dirty,
   пока ещё есть значение, ожидающее debounce. Отдельный тест удерживает и B,
   и следующий BASE, поэтому быстрое последнее подтверждение не маскирует откат.
6. **Обновление метаданных сбрасывало авторство прежнего Yjs-документа.**
   Отдельно воспроизведено: собственная запись принята с sequence 1, комната
   завершена, та же задача переименована, затем доставлена следующая собственная
   запись с исходной base 0. `syncFromRoom` сохранял документ и sequence, но
   терял карту авторов последовательностей и последнего автора delta. Поэтому
   HTTP 204 и relay не приводили к сохранению новой полной копии: в PostgreSQL
   оставался прежний текст. При неизменных публичном шаге и UUID задачи теперь
   вместе с документом сохраняются эти два поля проверки полномочий. Запись
   со старой базой по-прежнему не заменяет canonical при пропущенной чужой
   последовательности; snapshot heartbeat разрешён только прежнему последнему
   автору. Для новой задачи или шага авторство не переносится.

Обнаружена и устранена связанная ошибка области записи: ожидающий Markdown
был привязан к числовому шагу, который мог смениться при публикации или удалении
задачи. Новые запросы захватывают UUID исходной задачи. Последняя разрешённая
публичная правка сохраняется в прежнюю задачу после публикации другого шага.
Удалённый UUID вызывает конфликт, а приватная запись не перепривязывается при
восстановлении подписки к задаче, занявшей прежний индекс. Первое приватное
редактирование до SSE получает исходный текст из REST и UUID из состояния комнаты.

## Основные изменения

- [RoomPage](../../frontend/src/pages/RoomPage.tsx): ограниченный debounce,
  сохранение контекста исходной задачи, защита нового ввода от старого подтверждения.
- [useRoomSocket](../../frontend/src/features/room/useRoomSocket.ts): срок запроса,
  очередь, серверные версии, восстановление подписки, удержание и повтор намерения.
- [markdownDraftRecovery](../../frontend/src/features/room/markdownDraftRecovery.ts):
  перенос приватного черновика через canonical изменения и различение старого
  подтверждения от внешней правки.
- [CollaborationService](../../backend/src/main/kotlin/com/interviewonline/service/CollaborationService.kt):
  серверная проверка UUID задачи с сохранением проверок роли, комнаты и lifecycle;
  сохранение авторства при обновлении метаданных того же публичного Yjs-документа.

При подтверждённом отзыве manager-роли или запрете записи приватные recovery
данные и защищённая очередь очищаются. Поздний callback не создаёт их заново;
повторное назначение роли не восстанавливает старые приватные правки. Эти данные
находятся только в памяти, не сохраняют токены в UI recovery storage.
При заморозке с сохранённой manager-ролью отмена ожидающих заметок и чата
сообщается UI до очистки очереди: текст остаётся явно неотправленным рядом с
следующим черновиком. Отзыв права доступа не восстанавливает приватный текст.

Девять браузерных сценариев используют реальные API/SSE и управляемую задержку
реальных запросов:

1. Несколько секунд непрерывного ввода: промежуточная отправка, полное сохранение,
   совпадение после перезагрузки.
2. Зависший POST: отмена по сроку, reconnect, сохранение всего нового текста.
3. Конкурирующая внешняя правка приватного условия: обе правки сохраняются один раз.
4. HTTP 409 до задержанного SSE: Markdown и заметка за ним сохраняются без нового ввода.
5. Публикация другого шага при ожидающей записи: прежняя задача получает текст,

6. Отзыв и повторное назначение интервьюера: старый приватный черновик не возвращается.
7. Отзыв роли до окончания публичного debounce: старый таймер не пишет после нового назначения.
8. Первый приватный ввод до первого SSE: правильные исходный текст и UUID, без дублирования.
9. BASE → ожидающий B → BASE: старое подтверждение B не меняет редактор,

## Разбор отказов проверочного набора

- Свежие five-participant и public-step тесты сначала пытались нажать строку
  скрытой вкладки шагов, которую перекрывала текущая панель. Обновлён только путь
  теста: открытие видимой вкладки «Шаги», затем выбор строки. Для приватного кода
  добавлено ожидание фактической гидратации исходного текста. Проверки доступа,
  публикации, данных и задержки сохранены; `force` click не применялся.
- Первый полный Markdown прогон после обновления приложения дал 8/9: тест
  непрерывного ввода не увидел ни одной попытки. В отдельном повторе тот же
  production код прошёл. Начальная готовность теста усилена: он ждёт разрешённый
  для ввода редактор с canonical текстом, а не только получение SSE. Итоговый
  полный повтор 9/9 прошёл. Первоначальный отказ не считается доказательством
  исправления и не выдаётся за успешный прогон.
- Попытка обхода frontend proxy прямым API другого origin завершилась таймаутом
  настройки браузерной fixture; для доказательных прогонов использован обычный proxy.
- Полный набор выявил настоящую регрессию новой readonly-очистки: 2/4 существующих
  queued-notes тестов не прошли, поскольку очередь удалялась до уведомления UI
  об отменённой доставке. Для подтверждённого manager добавлены прежние callbacks
  до удаления записей. Неизменённый набор затем прошёл 4/4, а полный Markdown
  набор после этой правки и проверки роли снова прошёл 9/9. Логи:
  `.run/oct02-validation/editor-frozen-queued-notes-final.log` и
  `.run/oct02-validation/markdown-final-nine-authority-guard.log`.
- В общем прогоне lifecycle тест иногда завершал комнату до того, как пять
  быстрых `.fill` реально становились транзакциями EditorView. Добавлены
  ожидания пяти транзакций модели и фактического исходящего последнего значения
  при удержанном ACK; полный набор прошёл 10/10
  (`/tmp/lifecycle-final-deterministic-queue.log`). Завершение само по себе не
  вызывает `syncFromRoom`, поэтому этот отказ не выдаётся за доказательство
  отдельной ошибки обновления Yjs-метаданных. Для неё приведён собственный
  PostgreSQL RED с дополнительным переименованием той же задачи.
- Последующий общий прогон обнаружил независимую задержку общего фонового saver:
  блокировка строки комнаты A задерживала durable запись уже принятого текста B.
  Отдельный PostgreSQL RED воспроизвёл этот отказ. Saver теперь повторяет занятую
  строку без удержания общего исполнителя и сохраняет pending snapshot до commit;
  retained activity учитывается даже после закрытия последнего SSE.
  Новый regression 7/7 и связанные 33/33 — PASS, независимый review — APPROVE.
  Контракт — [P2.1 R-03/AC-11](../features/p2-1-room-layout-modes.md),
  общий результат — [итоговая проверка](2026-10-02-room-fixes-validation.md).

## Независимый review и границы

В review устранены ранний 409 до SSE, порядок sequence при повторе, очистка при
отзыве/readonly, UUID до первого private SSE и запрет переноса старого черновика
в заменившую задачу. Дополнительная узкая проверка undo guard также APPROVE.
Отдельно проверены readonly callbacks ожидающих заметок и перенос двух полей
авторства Yjs: APPROVE, с проверками чужого автора и finished candidate.

После изменений Yjs-метаданных и изоляции saver выполнена чистая повторная
проверка: backend 380/380, frontend unit/contract 76/76, typecheck/build PASS,
все 93 browser файла PASS. Markdown 9/9 и lifecycle 10/10 прошли в общем
повторе; отдельный context 19/19 и multi-participant 2100 сохранённых событий
также PASS. Текущий fingerprint, ограничения и сохранённые первоначальные
отказы приведены в [общем отчёте](2026-10-02-room-fixes-validation.md).

Неподтверждённый черновик живёт в памяти открытой страницы: закрытие страницы до
доставки не является гарантированным offline сохранением. Автоматический перенос
пересекающихся приватных замен сохраняет оба текста; он не разрешает смысловой
конфликт между авторами. Этот отчёт подтверждает перечисленные требования и
регрессии; он не утверждает покрытие всех возможных действий, устройств и отказов проекта.
