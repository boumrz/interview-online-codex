# AUTH.1 — проверка Google и GitHub, 17 ноября 2026

Действующий договор: [AUTH.1](../features/auth-1-social-login.md). Проверена реализация Google/GitHub и защищённого возврата в комнату. Живые внешние аккаунты и целевой production-прокси не проверены. Флаги выпуска выключены по умолчанию.

## Среда и результаты

Проверки использовали Java 17, PostgreSQL 16 с отдельными схемами и HTTP-заглушки провайдеров. Изолированный браузерный runner копировал backend во временный каталог и поднимал отдельные процессы. Рабочее приложение пользователя не перезапускалось.

Итого 33 различных backend-теста и 17 браузерных сценариев. В браузерных сценариях ответы OAuth подменены; профиль и комната используют API изолированного приложения. Это не подтверждает настройку реальных сервисов.

Независимый обзор реализации авторизации: **approve** после исправления обоих конфликтов журналирования. Проверены владение внешней личностью, state/PKCE/браузерная cookie, Google claims, минимальные GitHub scopes, возврат с выданной сессией и конкурентные вставки. Итоговый повторный обзор подтвердил безопасный отказ `NICKNAME_TAKEN` и восстановление той же попытки; открытых блокирующих замечаний по коду не осталось. Внешние проверки перед выпуском этим обзором не заменены.

## Исправления, подтверждённые отказом проверки

- Браузерный сценарий возврата в комнату выявил, что публикация сессии вызывала переход в кабинет раньше завершения навигации. Теперь разрешённый путь фиксируется до публикации сессии и используется обоими путями навигации; сценарий возвращает кандидата в ту же комнату.
- Конкурентная вставка одной пары `provider + subject` могла вывести subject в SQL-диагностику. Вставка `ON CONFLICT DO NOTHING` возвращает контролируемый конфликт без исключения БД. Проверки гонок регистрации и привязки контролируют одного владельца и отсутствие таких SQL-сообщений.
- Для двух разных внешних личностей, одновременно выбравших один ник, тест удерживает таблицу `users` до достижения обеими транзакциями вставки. RED воспроизводил необработанную unique-ошибку с ником в логе и неверный код `SOCIAL_IDENTITY_CONFLICT`. Теперь вставка социального пользователя использует `ON CONFLICT (nickname) DO NOTHING`: один аккаунт и одна сессия, второй ответ `NICKNAME_TAKEN`, профиль и ник отсутствуют в captured output. Та же попытка успешно продолжается с исправленным ником. Эта проверка выполняется на PostgreSQL, поскольку проверяет транзакции, блокировки и фактическое журналирование JDBC/Hibernate.

## Воспроизведение

С корня репозитория, с установленными Java 17 и доступной тестовой PostgreSQL:

```sh
JAVA_HOME=/Library/Java/JavaVirtualMachines/temurin-17.jdk/Contents/Home mvn -q -f backend/pom.xml -Dtest=SocialAuthIntegrationTest,SocialAuthMigrationIntegrationTest test
JAVA_HOME=/Library/Java/JavaVirtualMachines/temurin-17.jdk/Contents/Home mvn -q -f backend/pom.xml -Dtest=SocialAuthConfigurationTest,SocialAuthDisabledIntegrationTest test
```

Из `frontend/`:

```sh
FEATURE_SOCIAL_AUTH_ENABLED=true FEATURE_LEARNING_ENABLED=true node tests/e2e/run-isolated.mjs tests/e2e/account/e2e-social-login.mjs
node tests/e2e/run-isolated.mjs tests/e2e/account/e2e-social-login-disabled.mjs
npm run typecheck
```

Локальные логи последних целевых запусков: `/tmp/interhub-auth-nickname-red.log`, `/tmp/interhub-auth-nickname-green.log`, `/tmp/interhub-auth-e2e4.log`, `/tmp/interhub-auth-disabled-e2e.log`. Они не входят в репозиторий и не являются долговременным артефактом.
